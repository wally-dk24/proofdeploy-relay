1. **In-app dump (generic Django):** run inside the app's own interpreter in the sandbox (same mechanism as the Flask dump; `DJANGO_SETTINGS_MODULE` from the app env): walk `django.urls.get_resolver()` recursively; for each pattern produce method(s), path template (`{name}` params from converters/regex groups, with types int/str/slug/uuid/path), and the view.
2. **DRF shapes:** for DRF views/viewsets (routers included: list/create/retrieve/update/partial_update/destroy and `@action`s with their methods), read the serializer (`get_serializer_class()` on an instance with a fake request where needed; fall back to `serializer_class`) and build a JSON schema per method from its fields: type, required, allow_null, read_only (excluded from request bodies), max_length/min_length, min/max value, choices (enum), nested serializers (object), ListField/many (array), PrimaryKeyRelatedField (integer id, marked `reference`). Plain Django views: route only, no body schema.
3. **Ordering:** published OpenAPI first (as today), then Flask, then Django; else `cannot_map`. The manifest records `mapped_by` (`openapi` | `flask` | `django_drf` | `django`) and, per side, the request acceptance rate (non-4xx share of loop requests).
4. **Tests on the synthetic DRF app (host mode):** the index lists exactly its routes with the right methods and path params; a serializer with required, read-only, max_length, choices, nested and a reference field gives the right schema; a plain Django view gives a route with no body; the generator's seeding stage uses these shapes (valid creates get 2xx). Plants: read_only fields left in bodies; router actions missed; ordering puts Django before OpenAPI — each caught.
