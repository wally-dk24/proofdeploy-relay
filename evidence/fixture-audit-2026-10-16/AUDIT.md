## 0. The measured path, traced once (common to every unit below)

**Driver.** A measured unit runs via `.github/workflows/measure.yml`: it clones the *pristine target repo* (`git clone "$TARGET_REPO" /tmp/target-repo`, measure.yml:100) and invokes `python -m proofdeploy.cli measure --repo /tmp/target-repo --bug-id/--base/--bug/--fix` or `--clean-id/--clean` (measure.yml, "Run measured unit" step). `cmd_measure` (`proofdeploy/cli.py:268`) builds a `MeasureConfig` and calls `Orchestrator.measure_bug()` (`proofdeploy/orchestrator.py:2006`) or `measure_clean()` (`orchestrator.py:2329`).

**Where the fixture text comes from (Q1 mechanism).** `measure_bug` calls `_build_bundle(rev_base=B^, rev_tip=B)` and `measure_clean` calls `_build_bundle(rev_base=C^, rev_tip=C)` (orchestrator.py:2052, :2364). `_build_bundle` (orchestrator.py:586) snapshots the tip rev and loads the contract **from inside that snapshot**:

- orchestrator.py:622 — `contract = load_contract(snapshot.dir / "proofdeploy.yml")`
- orchestrator.py:631-642 — `assemble_author_bundle(..., yml_fixture=contract.fixture, ...)` with the template chosen at :628 by `template_filename(contract.auth is not None)`.
- `proofdeploy/fixture.py:466` — `assemble_author_bundle` calls `render_description(template_text, yml_fixture)`; the rendered text becomes the bundle's `fixture-description.txt`, which is embedded in the author prompt.
- The same load-from-snapshot rule holds for provisioning: each side's contract is `load_contract(snapshot.dir / "proofdeploy.yml")` (orchestrator.py:1215 and :1293). For a bug unit the bundle contract comes from the **B tree** while the side contracts come from the **fix^ and fix trees**; for a clean/control unit everything comes from the **C tree**.
- The answer-key/leak check recomputes the same render (`proofdeploy/leakcheck.py:298`: `render_description(template_text, contract.fixture)`), so there is no second, more forgiving path.

**The readiness contracts are a different file that the measured path never reads.** `readiness/contracts/<owner__repo>.yml` enters a tree only through the *readiness* harness: `readiness/provision.py:174` `commit_contract()` creates one harness commit per side (parent = registered SHA, tree delta = exactly `+proofdeploy.yml`, provision.py:186-193), called at provision.py:593. Nothing in `proofdeploy/` imports or references `readiness/contracts/`; `measure.yml` never creates a harness commit. (Contrast: `proofdeploy verify` also reads the contract from the target repo's own checkout — verify.py:333 — i.e. a repo that carries its own `proofdeploy.yml`. The conformance golden apps do exactly that: `conformance/golden/*/revisions/*/proofdeploy.yml` carry full `fixture:` blocks in-tree, which is why the golden path renders and the D101 defect could happen there.)

**Loader semantics.** `fixture` is optional: `yml.py:130` — `fixture = data.get("fixture") or {}`, type-checked at :131-134. A contract with no `fixture:` parses fine and yields `contract.fixture == {}`.

**Render semantics (fail-closed, no fallback).** `render_description` (fixture.py:89) requires every field the selected template *uses* to be present and non-empty, else `ValueError("fixture mapping missing fields: …")` (fixture.py:112-131). The credential template uses all five fields (`fixture.py:28` `TEMPLATE_FIELDS`); the no-credential template uses four (no `{auth_scope}`). Template selection is mechanical (fixture.py:61): a top-level `auth:` mapping in the contract ⇒ `fixture_template.txt`; otherwise `fixture_template_nocredential.txt`.

**What the measured path does today for every unit in this audit — two failures, in order:**

1. **No `proofdeploy.yml` in the tree.** The registered SHAs are upstream commits; upstream trees do not carry ProofDeploy's contract file. `_build_bundle` raises `FileNotFoundError` at `load_contract` (`yml.py:459`, `Path.read_text`) — reproduced: `FileNotFoundError: [Errno 2] No such file or directory: '…/proofdeploy.yml'`. `FileNotFoundError` is not an `OrchestratorError`, so it escapes `measure_bug`/`measure_clean`; `cmd_measure` catches only `OrchestratorError`, and `main()`'s generic catch (cli.py:345) prints `proofdeploy: error: …` and exits 2. **No evidence record, no score, no model call.** This fires before the fixture question is even reached.
2. **Even with the readiness contract placed in-tree** (the harness-commit shape), `contract.fixture == {}` and the render raises `ValueError` — reproduced verbatim per contract in §1–§4 below. Same escape path, same exit 2. There is no default, no empty-string render, and no skip: the run dies in bundle assembly.

**Auth in the measured path (Q2 mechanism).** The executor for each side is built by `_make_executor` (orchestrator.py:1951) with `credential_config=self._credential_config(side)` (orchestrator.py:1976) and `fixture=dict(side.contract.fixture)`, `auth_token=None`. `_credential_config` (orchestrator.py:1868) returns the side contract's `auth:` mapping (minus `bootstrap_env`; for `ghost_jwt`+`key_file` it reads the key host-side after READY, :1890-1905), or **`None` when the contract declares no `auth:`** — its docstring (orchestrator.py:1871-1874): absent means no credential, `${AUTH_TOKEN}` is unknown, and a probe using it is INCONCLUSIVE `probe`, fail-closed. When a config exists, `Executor` constructs `CredentialProvider(credential_config)` (executor.py:690-692), whose modes are `register` / `login` / `refresh` / `ghost_jwt` (setup_auth.py:377; mode key sets validated at load, yml.py:64 `_AUTH_MODE_KEYS`). Provider semantics (setup_auth.py module docstring and `CredentialProvider` docstring, :377ff): `register` creates a **fresh disposable user per run** with generated credentials; `login` POSTs the declared body template, whose `${NAME}` placeholders resolve from the run's bindings — in practice the per-side bootstrap credentials; `refresh` acquires by login first when `login_path`/`login_body` are declared, then refreshes near expiry; `ghost_jwt` mints a short-lived JWT per request from the instance's admin key (setup_auth.py:330 `mint_ghost_jwt`). Bootstrap values are generated fresh per side and per run from the *names* in `auth.bootstrap_env` (`generate_bootstrap_env`, setup_auth.py:64; orchestrator `_side_bootstrap`), and the seed/bootstrap of that same side consumes the same values — so a `login`/`refresh` token belongs to **the account the side's own bootstrap created with those generated credentials**, never to a pre-existing upstream account.

**Whose token the author is *told* it holds (Q2, text side).** Only the rendered fixture description tells the author anything. The credential template's frozen suffix is: "Token scope: {auth_scope}. No other users, roles, or credentials exist beyond what the seed creates." and its header comment (fixture_template.txt:12-14) describes `${AUTH_TOKEN}` as "the disposable super-admin credential". The no-credential template says: "Authentication: {auth_mechanism}. You are given no token or credentials." and "No users, roles, or credentials exist beyond what the seed creates." For every unit below, **nothing is rendered today, so the author is told nothing** — the run never reaches the author.

**Per-repo fact.** Contracts are one file per repo, "identical across all of that repo's commits" (readiness/contracts/PROVENANCE.md:3-5). Fixture text therefore cannot be unit-specific within a repo; whatever is written serves every unit of that repo, present and future.

## 5. The walk's future units — where their fixture text and provider would come from

**Selection mechanism (registered).** Held-out Addendum 1 (docs/evaluation/held-out-addendum-1.md): bugs continue by the same rule over the same five repositories in order — **nestjs/nest, koajs/koa, adonisjs/core, pallets/flask, fastapi/fastapi** — advisories first, then strict `^fix(` commits in SHA order, continuing from the position after the last candidate judged on 2026-10-09 (H3); clean diffs by the same method continued (H4). Addendum 2 (J1/J3/J5): existing units are judged by the same rule, and removed units are replaced **only** by continuing this walk; the completed list is committed before any probe is authored or any measurement runs (H6/J5).

**Fixture text and auth for those units: no registration specifies either.** Neither addendum mentions `fixture`, a fixture description, or an auth provider at all (verified by full-text search of both addenda). What a future unit would hit, in order:

1. **A readiness contract must exist for its repo before H5 can even run.** `readiness/contracts/` at this SHA holds 10 repos; of the five walk repos only nestjs/nest has one. koajs/koa, adonisjs/core, pallets/flask and fastapi/fastapi have **no contract file** — a walk candidate from any of them first needs a contract authored by the Addendum-64 method (from the repo's HEAD README + config only, generic, with a PROVENANCE entry: PROVENANCE.md:3-9). That method, as practiced, produces contracts *without* `fixture:` blocks (all 10 current files lack one).
2. **For measurement, the §0 mechanism applies unchanged:** an in-tree `proofdeploy.yml` at the measured revs — which no step in the walk creates — carrying a `fixture:` mapping — which no registration requires anyone to write, review, or approve. The two 2026-10-09 approvals (Vendure, Directus) happened as stage-check by-products and survive only as hashes; there is no standing procedure that would produce an equivalent approval for a walk unit.
3. **Auth** would be whatever the new repo's contract declares (one of `register`/`login`/`refresh`/`ghost_jwt`, or none). The walk's Python repos (flask, fastapi) would additionally meet the Python lock rule; nothing in the walk registrations speaks to credentials for them.

**Conclusion for the walk:** future units get their fixture text from nowhere. The pipeline is unspecified at exactly the step this audit covers — selection and readiness are registered in detail; the fixture/provider layer that the measured path hard-requires (§0, failures 1 and 2) has no owner, no authoring step, and no approval step in any registration on main.

## 7. What surprised the auditor

1. **The measured path never reads `readiness/contracts/` at all.** The file the readiness program maintains enters trees only via readiness harness commits; `measure.yml` clones the pristine upstream repo and the orchestrator loads `proofdeploy.yml` from inside the snapshot. So every checkpoint and held-out unit would today die at `load_contract` with `FileNotFoundError` — *before* the fixture gap, before the answer-key check, before any model call, and with no evidence record written. The fixture problem is the second failure, not the first.
2. **Two reviewer-approved fixture descriptions exist only as sha256 hashes.** Vendure's and Directus's approved texts (2026-10-09) cannot be reconstructed from anything in the repo; the readiness contracts expressly derived from them dropped the `fixture:` block in transit.
3. **The one approved auth wording in the repo ("static Bearer token", Directus) contradicts the provider that would serve it** (login+refresh, short-lived tokens) — a D101-shaped text-vs-mechanism mismatch already sitting in a registration.
4. **Template selection is a silent side effect of the `auth:` key.** Adding or removing an auth block flips which frozen template the author receives and which fields become mandatory; nothing in the readiness path renders, so the flip is invisible until a measured run.
5. **Vendure's registration history and its contract disagree about whether Vendure has a credential at all** — stage checks exercised auth with a 1-year lifetime (PASS for C1 and C2), while the contract declares no provider and no fixture.
6. **For bug units the bundle contract is read from the B (bug-introducing) tree**, the oldest tree in the unit, while side contracts come from fix^/fix. One-contract-per-repo practice masks this, but the code does not require the three trees' contracts to agree — the leak check renders from the B-side contract only.
7. **Ghost's checkpoint readiness contract provisions an app with no owner, no seed, and no credential** — the most "held" unit is also the one whose measured form is furthest from the fixture text currently being finalized for it on PR #121.
