Seed data: The first migrate run on an empty database created one application-settings record (from the app's own first migration) whose fields are all empty, so the app's defaults apply; the permission and content-type records Django generates for every installed model; and one user named AnonymousUser with an unusable password (created by the django-guardian library). ProofDeploy's setup then ran the app's own manage_superuser command, which created one superuser whose username and password are generated fresh for each run and whose email is root@localhost. No groups and no content were created.
Authentication: the token is presented in the Authorization header in the form 'Token <token>'. Your token: ${AUTH_TOKEN}.
Token scope: the API token belonging to the generated superuser; ProofDeploy obtains it by signing in as that user, the first sign-in creates it, and later sign-ins return the same token. No other users, roles, or credentials exist beyond what the seed creates.
Feature flags: application settings are at this version's defaults except the run's deployment choices (SQLite database, in-memory cache and channel layer) and the token sign-in rate limit, raised to 600 per minute (PAPERLESS_TOKEN_THROTTLE_RATE); no feature flags were changed.
You may create users, roles, data, or change settings in setup steps before your probes run.
