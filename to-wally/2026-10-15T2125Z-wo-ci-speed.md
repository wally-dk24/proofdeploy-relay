# Work order: CI wall-clock optimization

**Plan line:** 1.13 CI and gate upkeep (D21). **Master's direction (reviewer chat, 10-15 ~17:05 EDT, verbatim):** "As we adding more tests- do you see an option to shard them more so that we get to run tests quickly. Im not compromising on tests- I want optimization of CI".
**Hard constraint:** every test still runs on every PR and every main push. The exact-set manifest proof (WAL-109), the no-skip JUnit verification (A55), the 80% coverage floor and the required `test` check stay as they are.

## Why "more shards" alone would make it slower
- Each push starts **23 jobs**: ci = `changes` + `lint` + 3 host shards + `test`; sandbox-tests = `changes` + 16 shards.
- On the Free plan GitHub runs **at most 20 jobs at once** for the account (docs.github.com/en/actions/reference/limits). One push already queues; the freshness rule (D51) refreshing 2–3 PRs at once means 50–70 jobs in waves. Today's "deep runner queue" is that.
- Every job also pays a fixed cost before any test runs: setup-python + `pip install`, a ~2-minute collection (the podman capability probe runs at import time; the `ci.yml` comment measures it), and on sandbox jobs an `apt-get install podman` plus image pulls. The count step and the pytest step each collect.
- So the wins are: cut the fixed cost per job, then fit the jobs to the 20-job cap, balanced on measured time.

## Tasks
1. **Measure first (no changes).** From the API, over the last 10 runs of both workflows (main pushes and PRs), post a table per job: queued time, total time, and time per step (setup, pip, podman install, image pulls, the count step, pytest). Add per-file test durations from the JUnit reports. This is the baseline every claim is checked against.
2. **Lazy capability probe** (radar item). The podman probe runs on first use, never at import. Proof: the collected nodeid set and the sandbox marks are identical before and after (the manifest check passes **unchanged**, with no regeneration), and collection time is shown before and after.
3. **Collect once per job.** Take the shard's count from the same pytest run (collect-only output or the JUnit report) instead of a second collection. The A55 verify keeps asserting tests == expected and skipped == 0, where expected comes from the manifest, so a test that silently didn't run still fails the job.
4. **Cache the fixed setup on sandbox jobs:**
   - First check whether the runner image already ships podman (`podman --version` before apt); install only if missing.
   - Cache the pinned images by digest (pull once, `podman save` into the actions cache keyed by the digest list; `podman load` on hit; a digest mismatch is a cache miss, never a silent substitute).
5. **Re-pack the shards to the cap, by measured time.** Write a script that packs files and nodeids into shards from the JUnit durations of the latest main run (largest-first bin packing). It writes the matrices and regenerates the manifest. **Target ≤ 20 jobs per push across both workflows**, with the critical path minimized, i.e. the slowest shard's total time (setup + tests). Merge sandbox shards whose setup outweighs their test time; split the heavy ones. Commit the script, so rebalancing is one command as tests grow.
6. **Before/after evidence.** Three PR runs and one main run after the change: time from push to all-green, the slowest job, total queued time, and a jobs-per-push count. The total test count and nodeid set must be identical to before; coverage unchanged or higher.

## Plants
- (a) Make one test skip on a host shard → the A55 verify fails.
- (b) Drop one file from the packed matrices → the manifest check fails with the nodeids named.
- (c) Corrupt one cached image digest → cache miss and a fresh pull, never a load of the wrong image.

## Done when
Tasks 1–6 are posted, the plants are caught, CI is green, the pins are unchanged, and the manifest is OK. Wall-clock from push to green is lower on the measured runs, and no test has been removed, skipped or deselected. Report the numbers; if a step didn't help, say so and revert it.
